## 2026-09-04 — The public read-only demo identity

**Why.** tekguyz.com's `/work/tekguyz-crm` case study linked to this app and an
anonymous visitor landed on `/login` — a dead end. The case study claimed a
build existed and then offered no way to see it.

**What shipped.** `https://tekguyz-crm.vercel.app/demo` — one GET, one redirect,
no signup, no password, no interstitial. Behind it is a permanent identity that
holds `SELECT` and nothing else, so it can be published without a reset job, a
cron, rate limiting, or any concern about what a stranger might write.

### The mechanism, and why the obvious one was wrong

The read-only guarantee is a **dedicated Postgres role, `demo_readonly`**, not a
new `VIEWER` value in `organization_members.role`.

The OWNER/ADMIN/MEMBER model lives *above* RLS, inside policy predicates.
Making a `VIEWER` value read-only would have meant a clause added to **9 write
policies** (`leads` ×2, `activity_logs`, `tasks` ×2, `prospects` ×2,
`lead_submissions`, `organization_members`, plus the `storage.objects` upload
policy) **and** a guard added to **9 `SECURITY DEFINER` RPCs**, because a
`SECURITY DEFINER` function runs as its owner and ignores policies entirely:
`import_leads_chunk`, `import_prospects_chunk`, `create_organization_with_owner`,
`accept_organization_invite`, `change_member_role`, `remove_organization_member`,
`vault_set_org_credential`, `vault_clear_org_credential`, `get_org_webhook_secret`.

Eighteen edit sites, each of which must be remembered again for every table and
every RPC added later. **A forgotten clause is a silent write hole.** It fails
open.

Grants are checked *below* RLS. A role holding only `SELECT` is denied every
write on every table with no policy edits, is denied all nine RPCs for free
(no `EXECUTE` grant), and — because Supabase's default privileges grant new
`public` tables to `anon`/`authenticated`/`service_role` and deliberately not to
`demo_readonly` — **a table added next year is unwritable by this role from the
moment it is created.** It fails closed.

**The finding that made it cheap: not one policy in this schema carries a `TO`
clause.** Verified across every migration. They all default to `PUBLIC`, so they
apply to any Postgres role, and `demo_readonly` is covered by the existing read
policies unchanged — still `organization_id in (select private.current_org_ids())`,
still keyed on `auth.uid()`, still resolved through exactly one
`organization_members` row. No second tenant-resolution path was introduced,
which CLAUDE.md's rule 1 forbids.

### How the role reaches a request

PostgREST does `set local role <the JWT's role claim>`. Two candidates could
supply that claim and neither had been run in this project, so the first
implementation step was a throwaway spike rather than a guess:

1. `auth.users.role`, which GoTrue copies into the claim.
2. A Custom Access Token Hook, which needs a Supabase dashboard change.

**Candidate 1 works.** A disposable user's claim moved from `authenticated` to
`demo_readonly` after one `admin.auth.admin.updateUserById(id, { role })` call.
No auth hook is configured and none should be added. `scripts/seed/lib/demo-visitor.ts`
re-asserts both the role and the password on every seed run, so a manual
dashboard edit cannot silently leave the account writable, and rotating the
credential is an env change plus a reseed.

### Fails closed, demonstrated on day one

The first migration granted `SELECT` on eight tables and `EXECUTE` on exactly
one function, `private.current_org_ids()`. The demo could then read every table
it needed and **render no page at all**: `src/app/(app)/layout.tsx` — the app
shell, so every route — calls `public.get_organization_members`, and every page
returned "Something went wrong" with `42501 permission denied for function`.

That is the design working. The first thing that went wrong was the demo being
too locked down, visible on the very first page load. The `VIEWER` failure mode
is a stranger writing to the database, which is visible never.

A second migration (`20260904130000`) grants that one function, narrowly and
after reading its body: it is `stable` so it cannot write, it is self-scoping
(`and p_org_id in (select private.current_org_ids())` in its own `WHERE`), and
it returns no secret. **It is the only function grant this role gets**, and that
was established by probing every read the app performs on a render path in one
pass rather than shipping one migration per bug.

### A real email address was one grant away from being public

`get_organization_members` returns each member's `auth.users` email and the app
shell renders that list on every page. Once `/demo` was public, every member
email in `TEKGUYZ Demo` was on a page strangers could read — and that included
`opsmiller85@gmail.com`, a real address, appearing twice: as a MEMBER and as an
ACCEPTED invite.

`scripts/seed/lib/demo-membership-hygiene.ts` now redacts every non-`@example.com`
membership and invite from the demo org on each seed run. `@example.com` is
reserved by RFC 2606 and can never be a real mailbox, which makes it the one
unambiguous signal that an address in a public demo is synthetic. Auth accounts
themselves are never touched, and the helper refuses to strip an org's last
OWNER.

### The weekly-report leak, fixed as an independent bug

`/api/cron/weekly-report` swept every organization, so `TEKGUYZ Demo` had a
Gemini executive narrative billed and a Resend send posted to
`tekguyz.demo.owner@example.com` — an address that can only bounce — every week.
`create-demo-org.ts` printed a warning about exactly this the day the demo org
was built, and it was never actioned. The sweep now carries
`.eq("is_demo", false)`. Excluded at the query rather than skipped inside the
loop, so nothing downstream runs at all. Verified live: `TEKGUYZ` is swept,
`TEKGUYZ Demo` is not, and no other org's behaviour changes because `is_demo` is
`NOT NULL DEFAULT false`.

### Voice memo: strictly read-only, and one ordering rule

The original brief asked for voice memo capture to "work end-to-end as a
recording" while the account had "zero ability to write anything". Those cannot
both be true — saving a memo inserts an `activity_logs` row and uploads a
storage object. Resolved in favour of strict read-only: an `activity_logs`
carve-out would have broken the guarantee and handed a stranger an unbounded way
to fill the table and the bucket, with no reset job to clean it.

The Gemini skip was added anyway, per the brief, so the guarantee does not
depend on the grant being right. **It sits above `transcribeOrFallback` and that
is load-bearing**: `resolveOrgCredential` falls back to `PLATFORM_GEMINI_API_KEY`,
so a guard placed below it would stop holding the moment that var is set — which
it is, in production. Nothing fails if someone reorders them: green build, every
other test passes. `audio-transcription.test.ts` asserts the ordering at the
source level, the same shape as the `outline-none` guard in
`dropdown-menu.test.tsx`, and was proven to fail before the guard existed.

### Two things found by measuring rather than assuming

**The demo org had no tasks at all.** It seeded leads, `activity_logs` and
prospects, so Agenda, Today and the calendar all rendered empty for a visitor —
which reads as an unfinished feature, not an empty state. `scripts/seed/lib/demo-tasks.ts`
adds eight, spread across overdue, due today and upcoming, plus two completed.
The overdue ones are what exercise the Going Cold SLA styling. No wipe function:
`tasks.lead_id` is `ON DELETE CASCADE`, so `wipeDemoLeads` already removes them.

**Supabase Storage does honour `demo_readonly`.** The design spec flagged as an
open risk that Storage, being a separate service with its own JWT handling,
might assume `authenticated`. It does not — the demo identity lists
`audio-notes` successfully and sees only its own org's folder. The risk did not
materialise and needs no gap entry.

### A standalone `tsc --noEmit` was green only by accident

Found while verifying this wave, and fixed in it: clearing `.next` made `npx tsc --noEmit` start failing with `TS2882` on both side-effect CSS imports (`layout.tsx` and `global-error.tsx`), on an **untouched checkout** — confirmed by stashing every change in this wave and re-running. Next supplies no declaration for a plain stylesheet: `next/types/global.d.ts` covers `*.module.css` and `*.module.scss` only. `next build` passes regardless, because it runs its own type check that already understands the import, so the gap is visible **only** to the standalone `tsc` a session uses to decide the tree is clean. What had been hiding it was a stale artifact from an older Next version sitting in untracked `.next/` — not regenerated by 15.5.20, and gone the moment the directory was cleared. `src/globals.d.ts` now declares `*.css` in one line, so the guarantee no longer depends on build output.

### Verification

`src/lib/demo/demo-visitor.rls.test.ts`, 26 assertions in `npm run test:rls`,
run against the **real** seeded identity and the real `TEKGUYZ Demo` org rather
than a disposable stand-in — a fixture with the same role would not prove that
*this* account is safe. It creates no rows on the happy path, since every write
it attempts is expected to fail, and `afterAll` removes anything that got
through.

One of those tests passed vacuously on its first run: "denies UPDATE on tasks"
returned early because the demo org had no tasks. Replaced with a service-role
fixture task created in `beforeAll` and removed in `afterAll`, so it can never
pass without actually attempting the write.

Through the real UI, the real Server Action and the real database, clicking the
rendered, non-hidden Dismiss control produced:

```
Error: {"code":"42501","message":"permission denied for table tasks"}
```

That is the distinction that mattered: the control is present and clickable, and
Postgres refuses. Nothing is merely hidden.

### Tooling gap closed on the way

CLAUDE.md's standing temp-table dry-run rule was **unenforceable in this repo**:
no `pg` driver, no `psql`, and `supabase db push --dry-run` blocked twice — once
by a CLI account privilege error, then by migration-history drift (remote
carries `20260707215206`, absent locally; not repaired, since that writes to the
history table and is the human's call). `pg` is now a devDependency and
`scripts/dryrun-migration.ts` is the worked example the next migration copies.

Its limitation is stated in the file rather than hidden: `create role` and
`grant` are cluster-level, not session-local, so only the table DDL is genuinely
dry-run.

### Scope notes

Nothing under `src/app/api/v1/triage/` or `src/lib/webhooks/` was touched, no
`leads` DDL, no `LEAD_COLUMNS` change — tekguyz.com's live contact form is
unaffected. `/api/dev-login` keeps its `NODE_ENV === "development"` allowlist
unchanged: it signs in an OWNER, which is a genuinely dangerous identity, and
`/demo`'s reasoning does not transfer to it. No `robots.txt` was created.

## 2026-09-04 — The demo read-only badge, and why it is neutral (later same day)

**Why.** `/demo` shipped earlier the same day and the read-only guarantee was
invisible. The org name said "TEKGUYZ Demo", but that names the *tenant* — it
tells a visitor the data is a sample and says nothing about whether they can
save. The first screen alone carries fifteen controls that write, and New Lead
is the most inviting button on it, so the first thing a refusal did was arrive
as a full-page error with nothing having explained why.

**What shipped.** `src/components/shell/DemoModeBadge.tsx`, rendered for the
demo tenant only. Presentation only — the boundary is still the `demo_readonly`
Postgres role, and no grant, policy or RPC was touched.

### Header, not sidebar

`WorkspaceBlock` is `sr-only` when the sidebar is collapsed and absent entirely
on mobile, and a case-study link gets phone traffic. `Header.tsx`'s "exactly two
things" rule is not reopened: the badge renders for `is_demo` tenants only, so
every real tenant's header is byte-identical to before. `getCurrentOrg` already
selected the row, so this is one extra column on an existing embed and adds no
query to a path that runs on every render of every page.

### Three corrections an hour after it shipped

The first version was orange, said `Demo · read-only`, and abbreviated to `Demo`
below `sm`. All three were wrong, and each for a reason this project has already
written down.

**Colour.** Orange put it in the same pill as the SLA `Overdue` badges a few
pixels below it on the Today view — one colour carrying two unrelated meanings
on one screen, and the other one is a real alert. CLAUDE.md's rule is that
colour is signal, not decoration; read-only is a standing condition, not an
alarm. Neutral now.

**Text.** `Demo · read-only` spent half its width on a word the sidebar already
said and the inbound link already promised. `Read-only` is the one fact
available nowhere else, so it became the whole text — which also fits a 375px
header intact and removed the responsive abbreviation, which had been weakening
the message on exactly the devices most likely to open a case-study link.

**Definition.** The neutral pill measures 1.06:1 against the header, so the pill
shape was invisible and the badge read as loose text. A hairline restores it.
Measured live at 8.64:1 text contrast, no horizontal overflow at 375px.

### What is still open

The refusal itself is unchanged: a write Postgres denies still surfaces as the
app's generic error boundary. The badge warns; it does not soften the landing. A
friendlier refusal needs the error boundary to know the session mode, which is a
wider change than a badge. Tracked in `docs/KNOWN_GAPS.md`.

Three tests came with it (`src/components/shell/DemoModeBadge.test.tsx`), proven
to fail with the badge removed.

## 2026-09-05 — Signup is invite-only, and `/login` offers the demo

Public self-serve signup was **live**. `/signup` rendered an open account
creation form to any visitor, `/login` linked to it in as many words ("No
account? Sign up"), and `signUp` in `src/lib/auth/actions.ts` called
`supabase.auth.signUp` with whatever address it was given. Anyone reaching the
production URL could create an auth user; the only thing standing between them
and a tenant of their own was the `/onboarding` form, which
`create_organization_with_owner` would have honoured.

That is attack surface with no legitimate purpose. This product is internal
infrastructure for a services business, not SaaS: there is no billing model, no
ToS, and no review step. The only accounts that will ever exist are provisioned
by hand for one or two trusted collaborators.

### What the audit found, and what it did not

The audit checked every pre-auth-reachable route. `/signup` was the only public
account-creation affordance — `/forgot-password` creates nothing, `/demo` signs
in a powerless identity, and `/invite/[token]` is gated by the token itself.

One thing the docs implied that turned out to be false: `/invite/[token]` does
**not** create an auth user. It renders a preview via `get_invite_preview` and
then sends an unauthenticated visitor to sign in *or sign up*. Signup is not
redundant to the invite flow — it is a **step inside** it. Deleting the route
would have left an invitee with no way to get an account at all.

So the route stays and the gate moves onto it.

### The gate, and why it lives in the action

`src/lib/invites/signup-gate.ts` holds the verdict: a token must name an invite
that exists, is `PENDING`, and has not expired. The predicate itself
(`evaluateInvitePreview`) is pure and clock-injected, so it is tested without a
database.

Both `/signup` and `signUp` run it, and only one of those is the boundary. **A
Server Action is POST-able directly**, so a page that merely hides its form
proves nothing — the action re-runs the check and additionally requires the
submitted address to equal the invited one, which is what stops a leaked token
being spent on an attacker's own account. The page-level check exists so a
stranger sees a sentence instead of a form; the action-level check is what makes
the path closed.

Every refusal returns identical wording, so guessing tokens leaks nothing about
which ones exist. The email-mismatch message is deliberately different — that
caller already holds a live token, so there is nothing left to conceal from
them.

This is routing and presentation only. No policy, grant, RPC or migration was
touched, and none should be added to enforce it.

### Proven by attacking it, not by reading it

The dev server's real `signUp` action id was pulled out of the rendered form and
POSTed to directly, bypassing the page entirely:

- no token, attacker's email → `303 → /login?error=This invite link is not
  valid.`
- valid token, attacker's email → `303 → /signup?...&error=This invite is for a
  different email address.`
- valid token, invited email → reached `auth.signUp`, which answered with
  Supabase's own password-policy error and then its email rate limit.

That last one is the end of the road on this project: email confirmation is on,
and Supabase's built-in SMTP limit is the same blocker `docs/KNOWN_GAPS.md` has
recorded since the original build. It is nonetheless positive evidence — the
error came *from* `auth.signUp`, so the gate let the legitimate request through.
Six unit tests in `src/lib/auth/signup-gate-action.test.ts` assert the same six
outcomes against a mocked client, including that `auth.signUp` is never called
in any refusal.

Supabase also rejects `.invalid` and `example.com` addresses outright, which is
why the live probe ended up on the owner's own `+alias`. The probe invite was
deleted and `npm run check:residue` re-run clean; no auth user was ever created.

### `/login` now has somewhere to send a stranger

The signup link is gone. In its place is **View demo** → `/demo`, the same
`text-accent` inline-link treatment as "Forgot password?" beside it. Measured
live: the colour resolves to each theme's own `--accent` (light
`lab(43.55 14.45 -63.74)`, dark `lab(63.97 5.62 -55.18)`), underlined in both.

Before this, `/demo` had exactly one entry point — a link from tekguyz.com's work
page. Anyone arriving at the production URL from GitHub, a resume or word of
mouth hit a wall.

### Deliberately not done

Landing page, onboarding, OAuth and a "Request access" link were all considered
and left out; the reasoning is recorded in the P1 entry of `docs/ROADMAP.md` rather
than here.

## 2026-09-05 — Three registered gaps closed: leads CSV export, the `/reports` period filter, one dead declaration

Three independently-registered items from `docs/KNOWN_GAPS.md`, done in one pass
because none of them touches the other. No schema, no migration, no RLS policy,
no grant, and no change to `src/lib/webhooks/*` or any lead write path.

### Leads CSV export — `GET /api/leads/export`

A route handler, deliberately not a Server Action: the deliverable is a file, so
`Content-Disposition` can hand the browser a real download with a real filename,
where an action would have to push the whole CSV through the RSC payload and
rebuild it as a Blob on the client.

The column set **is** `LEAD_COLUMNS`, split on commas — `LEAD_EXPORT_COLUMNS` in
`src/lib/leads/export-csv.ts`. That is the whole point of the unit rather than a
detail: that one string already backs eight read sites, and a ninth hand-written
copy is the drift class that produced the field-parity bugs. A column added to
`leads` tomorrow joins the export by itself; a hand-list would have gone stale
silently, and an export missing a column still looks like a working export. A
test asserts the equality directly, so the constant cannot be quietly forked.

Three things are written into the file rather than assumed:

- **The handler authenticates itself.** `updateSession` in
  `src/lib/supabase/middleware.ts` exempts `/api/*` from its login redirect on
  purpose — an API call deserves a status, not an HTML login page — so a route
  under `/api` is **not** gated by the middleware. It calls `getClaims()` and
  returns a 401 of its own. `getCurrentOrg` would have redirected, which is the
  wrong answer for a download.
- **Formula-shaped values are neutralised** with a leading apostrophe on `=`,
  `+`, `-` and `@`, on top of RFC 4180 quoting. `client_name` is
  attacker-supplied through the public webhook, so `=HYPERLINK(...)` in a lead
  name is a real path to a live formula the moment an operator opens the file in
  Excel. CRLF line endings for the same reason — Excel on Windows is the
  realistic consumer.
- **Archived rows are included, and the filters above the button are ignored.**
  An export is an archive, not a view. A backup that silently dropped the rows
  the operator had filtered out would be wrong in the one way an export must not
  be. `archived` is itself a column in the file, so the reader can filter.

Entry point is an **Export CSV** button in the Contacts filter row, built on
`Button`'s `asChild` over a plain `<a download>` — plain, because `next/link`
would try to client-navigate a route that returns CSV.

Live-verified through the real route while signed in via `GET /api/dev-login`:
`200`, `text/csv; charset=utf-8`,
`attachment; filename="tekguyz-demo-leads-2026-09-05.csv"`, `Cache-Control:
no-store`, 20 data rows, header exactly `LEAD_COLUMNS`, and a comma-bearing
address correctly quoted.

### `/reports` period filter — All time / This month / Last month / This year

The three open decisions the gap bullet named were settled rather than
rediscovered, and all three live in `src/lib/reports/periods.ts`:

- **Timezone: the organization's own** (`organizations.timezone`, already
  surfaced as `orgTimezone` by `getCurrentOrg`). Never UTC, never the browser's.
  The aggregation runs on the server, where there is no browser zone to read,
  and "this month" has to mean the same month for every member of a tenant no
  matter where they are sitting.
- **Buckets: closed leads by `closed_at`, open pipeline by `created_at`.** When
  a lead was decided is the only date that makes a period's win rate or realized
  revenue mean anything. An open lead has no `closed_at` at all, so bucketing it
  that way would empty the pipeline figure entirely. `ABANDONED` still buckets by
  `closed_at` and still counts toward period totals; it is excluded from the
  win-rate denominator exactly as before — **the formula itself is untouched**,
  the filter only narrows its inputs.
- **No proration.** A period is a calendar boundary in the org's zone, full
  stop. A part-elapsed month reports the leads it actually has.

The boundary is `[start, end)` — `.gte()`/`.lt()`, never `.lte()` — which is what
keeps a lead landing exactly on a month boundary in one period rather than two.

Two implementation notes worth keeping. The UTC instant of a local midnight is
resolved in **two passes**, because the zone's offset is itself a function of the
instant: the first guess reads the offset in force at UTC midnight, which is the
wrong side of a DST change roughly twice a year. And the wall-clock formatter
uses `hourCycle: "h23"` rather than `hour12: false`, because the latter can emit
hour `"24"` for midnight under some ICU versions and would shift a boundary by a
full day.

Aggregation stays in JS. PostgREST has no `GROUP BY`, and both alternatives are
schema work — the filter is two extra `.gte()`/`.lt()` pairs on the two SELECTs
that already ran.

The bucketing rule was proven by a test that could not even import before this
unit existed (there was no period module at all), and whose boundary pair fails
against any UTC-only reading: in `America/Chicago`, September starts at
`2026-09-01T05:00:00Z`, so a lead closed at `04:59:59Z` is **August**, and one
closed at `05:00:00Z` is September. Verified live too — the seeded demo org reads
16 open / $146,750 / 67% win rate at All time, and 5 open / $33,250 / no decided
leads for This month.

The empty state now distinguishes an empty period from an empty tenant. "No leads
yet" for a quiet month would be a lie about the whole account.

### One dead declaration removed from `globals.css`

`input:not([type="checkbox"], [type="radio"]):focus-visible`'s `border-color:
var(--accent)` was **deleted, not promoted**. It lived in `@layer base`, while
`Input`/`Textarea`/`Select` each carry a `border-hairline` (or `border-danger`)
utility, and utilities sit in a later cascade layer — so the declaration lost on
every field in the app and never painted a pixel. The paired 1px `box-shadow`
accent ring was always the thing carrying the accessibility floor on its own, so
removing the dead line is a no-op visually. A comment in its place says so, and
says where a real focus border would belong instead (a `focus-visible:` utility
on the primitives).

Measured live rather than reasoned about, through both documented traps:
`:focus-visible` did **not** match a programmatic focus until a real key press
had happened in the tab, and the `box-shadow` read back as a transparent `0px`
shadow until transitions were suppressed — the same-task transition-lag artifact
that produced a wrong Known Gaps entry once before. With both handled, a focused
field reads `box-shadow: lab(43.55 14.45 -63.74) 0 0 0 1px` (the theme's
`--accent`) while `border-top-color` stays the hairline `lab(88.39 -0.16 -1.12)`
both before and after focus — which is the proof the deleted line was doing
nothing. The shipped rule now reads, straight out of the CSSOM:
`textarea:focus-visible { box-shadow: 0 0 0 1px var(--accent); outline: none; }`.
