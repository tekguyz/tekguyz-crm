## 2026-09-04 — The public read-only demo identity

**Why.** tekguyz.com's `/work/tekguyz-crm` case study linked to this app and an
anonymous visitor landed on `/login` — a dead end. The case study claimed a
build existed and then offered no way to see it.

**What shipped.** `https://tekguyz-crm.vercel.app/demo` — one GET, one redirect,
no signup, no password, no interstitial. Behind it is a permanent identity that
holds `SELECT` and nothing else, so it can be published without a reset job, a
cron, rate limiting, or any concern about what a stranger might write.

### The mechanism, and why the obvious one was wrong

The read-only guarantee is a **dedicated Postgres role, `demo_readonly`**, not a
new `VIEWER` value in `organization_members.role`.

The OWNER/ADMIN/MEMBER model lives *above* RLS, inside policy predicates.
Making a `VIEWER` value read-only would have meant a clause added to **9 write
policies** (`leads` ×2, `activity_logs`, `tasks` ×2, `prospects` ×2,
`lead_submissions`, `organization_members`, plus the `storage.objects` upload
policy) **and** a guard added to **9 `SECURITY DEFINER` RPCs**, because a
`SECURITY DEFINER` function runs as its owner and ignores policies entirely:
`import_leads_chunk`, `import_prospects_chunk`, `create_organization_with_owner`,
`accept_organization_invite`, `change_member_role`, `remove_organization_member`,
`vault_set_org_credential`, `vault_clear_org_credential`, `get_org_webhook_secret`.

Eighteen edit sites, each of which must be remembered again for every table and
every RPC added later. **A forgotten clause is a silent write hole.** It fails
open.

Grants are checked *below* RLS. A role holding only `SELECT` is denied every
write on every table with no policy edits, is denied all nine RPCs for free
(no `EXECUTE` grant), and — because Supabase's default privileges grant new
`public` tables to `anon`/`authenticated`/`service_role` and deliberately not to
`demo_readonly` — **a table added next year is unwritable by this role from the
moment it is created.** It fails closed.

**The finding that made it cheap: not one policy in this schema carries a `TO`
clause.** Verified across every migration. They all default to `PUBLIC`, so they
apply to any Postgres role, and `demo_readonly` is covered by the existing read
policies unchanged — still `organization_id in (select private.current_org_ids())`,
still keyed on `auth.uid()`, still resolved through exactly one
`organization_members` row. No second tenant-resolution path was introduced,
which CLAUDE.md's rule 1 forbids.

### How the role reaches a request

PostgREST does `set local role <the JWT's role claim>`. Two candidates could
supply that claim and neither had been run in this project, so the first
implementation step was a throwaway spike rather than a guess:

1. `auth.users.role`, which GoTrue copies into the claim.
2. A Custom Access Token Hook, which needs a Supabase dashboard change.

**Candidate 1 works.** A disposable user's claim moved from `authenticated` to
`demo_readonly` after one `admin.auth.admin.updateUserById(id, { role })` call.
No auth hook is configured and none should be added. `scripts/seed/lib/demo-visitor.ts`
re-asserts both the role and the password on every seed run, so a manual
dashboard edit cannot silently leave the account writable, and rotating the
credential is an env change plus a reseed.

### Fails closed, demonstrated on day one

The first migration granted `SELECT` on eight tables and `EXECUTE` on exactly
one function, `private.current_org_ids()`. The demo could then read every table
it needed and **render no page at all**: `src/app/(app)/layout.tsx` — the app
shell, so every route — calls `public.get_organization_members`, and every page
returned "Something went wrong" with `42501 permission denied for function`.

That is the design working. The first thing that went wrong was the demo being
too locked down, visible on the very first page load. The `VIEWER` failure mode
is a stranger writing to the database, which is visible never.

A second migration (`20260904130000`) grants that one function, narrowly and
after reading its body: it is `stable` so it cannot write, it is self-scoping
(`and p_org_id in (select private.current_org_ids())` in its own `WHERE`), and
it returns no secret. **It is the only function grant this role gets**, and that
was established by probing every read the app performs on a render path in one
pass rather than shipping one migration per bug.

### A real email address was one grant away from being public

`get_organization_members` returns each member's `auth.users` email and the app
shell renders that list on every page. Once `/demo` was public, every member
email in `TEKGUYZ Demo` was on a page strangers could read — and that included
`opsmiller85@gmail.com`, a real address, appearing twice: as a MEMBER and as an
ACCEPTED invite.

`scripts/seed/lib/demo-membership-hygiene.ts` now redacts every non-`@example.com`
membership and invite from the demo org on each seed run. `@example.com` is
reserved by RFC 2606 and can never be a real mailbox, which makes it the one
unambiguous signal that an address in a public demo is synthetic. Auth accounts
themselves are never touched, and the helper refuses to strip an org's last
OWNER.

### The weekly-report leak, fixed as an independent bug

`/api/cron/weekly-report` swept every organization, so `TEKGUYZ Demo` had a
Gemini executive narrative billed and a Resend send posted to
`tekguyz.demo.owner@example.com` — an address that can only bounce — every week.
`create-demo-org.ts` printed a warning about exactly this the day the demo org
was built, and it was never actioned. The sweep now carries
`.eq("is_demo", false)`. Excluded at the query rather than skipped inside the
loop, so nothing downstream runs at all. Verified live: `TEKGUYZ` is swept,
`TEKGUYZ Demo` is not, and no other org's behaviour changes because `is_demo` is
`NOT NULL DEFAULT false`.

### Voice memo: strictly read-only, and one ordering rule

The original brief asked for voice memo capture to "work end-to-end as a
recording" while the account had "zero ability to write anything". Those cannot
both be true — saving a memo inserts an `activity_logs` row and uploads a
storage object. Resolved in favour of strict read-only: an `activity_logs`
carve-out would have broken the guarantee and handed a stranger an unbounded way
to fill the table and the bucket, with no reset job to clean it.

The Gemini skip was added anyway, per the brief, so the guarantee does not
depend on the grant being right. **It sits above `transcribeOrFallback` and that
is load-bearing**: `resolveOrgCredential` falls back to `PLATFORM_GEMINI_API_KEY`,
so a guard placed below it would stop holding the moment that var is set — which
it is, in production. Nothing fails if someone reorders them: green build, every
other test passes. `audio-transcription.test.ts` asserts the ordering at the
source level, the same shape as the `outline-none` guard in
`dropdown-menu.test.tsx`, and was proven to fail before the guard existed.

### Two things found by measuring rather than assuming

**The demo org had no tasks at all.** It seeded leads, `activity_logs` and
prospects, so Agenda, Today and the calendar all rendered empty for a visitor —
which reads as an unfinished feature, not an empty state. `scripts/seed/lib/demo-tasks.ts`
adds eight, spread across overdue, due today and upcoming, plus two completed.
The overdue ones are what exercise the Going Cold SLA styling. No wipe function:
`tasks.lead_id` is `ON DELETE CASCADE`, so `wipeDemoLeads` already removes them.

**Supabase Storage does honour `demo_readonly`.** The design spec flagged as an
open risk that Storage, being a separate service with its own JWT handling,
might assume `authenticated`. It does not — the demo identity lists
`audio-notes` successfully and sees only its own org's folder. The risk did not
materialise and needs no gap entry.

### Verification

`src/lib/demo/demo-visitor.rls.test.ts`, 26 assertions in `npm run test:rls`,
run against the **real** seeded identity and the real `TEKGUYZ Demo` org rather
than a disposable stand-in — a fixture with the same role would not prove that
*this* account is safe. It creates no rows on the happy path, since every write
it attempts is expected to fail, and `afterAll` removes anything that got
through.

One of those tests passed vacuously on its first run: "denies UPDATE on tasks"
returned early because the demo org had no tasks. Replaced with a service-role
fixture task created in `beforeAll` and removed in `afterAll`, so it can never
pass without actually attempting the write.

Through the real UI, the real Server Action and the real database, clicking the
rendered, non-hidden Dismiss control produced:

```
Error: {"code":"42501","message":"permission denied for table tasks"}
```

That is the distinction that mattered: the control is present and clickable, and
Postgres refuses. Nothing is merely hidden.

### Tooling gap closed on the way

CLAUDE.md's standing temp-table dry-run rule was **unenforceable in this repo**:
no `pg` driver, no `psql`, and `supabase db push --dry-run` blocked twice — once
by a CLI account privilege error, then by migration-history drift (remote
carries `20260707215206`, absent locally; not repaired, since that writes to the
history table and is the human's call). `pg` is now a devDependency and
`scripts/dryrun-migration.ts` is the worked example the next migration copies.

Its limitation is stated in the file rather than hidden: `create role` and
`grant` are cluster-level, not session-local, so only the table DDL is genuinely
dry-run.

### Scope notes

Nothing under `src/app/api/v1/triage/` or `src/lib/webhooks/` was touched, no
`leads` DDL, no `LEAD_COLUMNS` change — tekguyz.com's live contact form is
unaffected. `/api/dev-login` keeps its `NODE_ENV === "development"` allowlist
unchanged: it signs in an OWNER, which is a genuinely dangerous identity, and
`/demo`'s reasoning does not transfer to it. No `robots.txt` was created.
